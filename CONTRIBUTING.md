# Contributing to exchange-lab

exchange-lab is a research and learning tool. Its value rests on one promise: the same
input gives the same output, byte for byte, on every machine, and every number in the
documentation can be printed again from the committed evidence. Most of the rules below
exist to keep that promise. A change that breaks one of them is not merged, however good
it is otherwise.

Read [`docs/ARENA.md`](docs/ARENA.md) before changing anything in `arena/`. Several of its
parameters are load-bearing in ways that are not obvious, and the document records which
and why.

## The rules a change has to keep

- **Integer arithmetic inside a session.** No `float` or `double` anywhere a session
  runs: strategies, the session, the accounting, importers and the tape. A `std::log` is
  free to differ between library versions and would silently break cross-platform replay.
  Statistics computed *after* the sessions (the report's means, intervals and
  corrections) may use `double`, and are labelled `derived` wherever they are recorded.
- **Never hand-edit `results/`.** Every number there, and every number the documentation
  quotes from it, is regenerated by `bench/run_evidence.sh` or `bench/run_arena_evidence.sh`
  and printed by `bench/summarize_results.py` or `bench/summarize_arena.py`. A number those
  scripts do not print has no evidence behind it.
- **A new importer comes with a hand-made sample and a test.** The sample goes in
  `examples/data/`, made up by hand so it carries no vendor's licence, and the test goes in
  `tests/test_data.cpp`. The importer's version string moves when what it writes changes.
  Never commit a real data file, a tape or a market file.
- **A new control comes with a planted defect.** Every control in
  [`docs/CONTROLS.md`](docs/CONTROLS.md) has a defect planted in `tests/test_arena.cpp`
  that makes it fail. A control nobody has seen fail has not been shown to work.
- **"Strategy", never "bot".** Everything that takes part in a session is a strategy. The
  built-in ones are the reference market. Never name anything with *latency* in it either:
  a strategy's `reaction_ns` is an input the experimenter chooses, not a measurement.
- **No new dependencies.** A hand-written Makefile, the C++20 standard library and nothing
  else: no CMake, no package manager, no third-party library. Python is used only by the
  scripts in `bench/` that summarise committed evidence, and needs only the standard
  library.
- **No network, no browser, no AI model** in anything the project builds. Data files are
  read from disk, never fetched.
- **Determinism is a contract.** If a change moves a hash, it changed behaviour. Say so in
  the pull request and say why it was intended. The suite fingerprints are pinned: moving
  one needs a suite version bump in `arena/suite.hpp`, never a silent re-pin.
  `tests/canonical.txt` is never re-recorded to make CI pass.
- **Every new term** in a report or a document gets an entry in [`GLOSSARY.md`](GLOSSARY.md),
  and every new command goes in [`docs/LEARN.md`](docs/LEARN.md) or the relevant document
  and must run as written.

[`CLAUDE.md`](CLAUDE.md) holds the full set of rules the code depends on, including the
engine's own (single-threaded matching, zero allocation after construction, no C-runtime
calls on the hot path).

## Before you open a pull request

On Linux and macOS use `make`. On Windows use `mingw32-make` in an MSYS2 UCRT64 shell.

```bash
make -j4 test      # the 9 test programs, debug build with invariants and library checks
make test-cli      # the sweep's and the suite's command lines, and the evaluator's controls
make test-lab      # installing a strategy of your own, end to end
make test-app      # the terminal app, driven through its commands
make test-data     # importers, calibration and replay (about 90 seconds)
make canonical     # every output that must match on every platform
```

Run them one at a time: `test-app` and `test-data` both write under `runs/`. On Windows,
also run `mingw32-make recipe-check`, because MSYS2's make silently drops whatever follows
byte 8,191 of a command. For a change to the engine, add `make memmove-check` and the
sanitizer build in [`CLAUDE.md`](CLAUDE.md).

A clean build has zero warnings under `-Wall -Wextra -Wpedantic`, and should stay that way.

## Adding a strategy

Strategies live in `arena/strategies/`, never in the engine (`include/px/`, `src/`). A
built-in strategy is a header plus one line in `add_named_strategy()` and its name in
`kStrategyNames`, which `test_arena` holds together. Adding one does not move the suite
fingerprints unless it changes the default line-up. A strategy of your own that you only
want to score needs no pull request at all: `make strategy` installs it into the lab
binaries only, and [`docs/LEARN.md`](docs/LEARN.md) (exercises 4 and 5) and
[`docs/RUNNER.md`](docs/RUNNER.md) show how it is scored.

## Commits and pull requests

- Work on a branch. Commit in coherent steps whose message says what changed and what the
  evidence was. Never commit a state where `make test` fails.
- Plan anything substantial in a markdown file before building it, and turn the plan into
  the design document when it is built. Keep the approaches that were wrong: they are the
  part worth reading.
- Fill in the pull request template. The fingerprint question matters most.
- Bugs go in GitHub Issues, using the bug template. The run fingerprint and the exact
  command are what make a report reproducible.
